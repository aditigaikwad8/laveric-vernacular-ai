CRITICAL / LIVE CALLING-HOME — CONFIRMED BY RUNTIME EVIDENCE
=====================================================================

FINDING A — Backend: live calls to services.dograh.com on every signup
During a test signup (02:51:14–02:51:22, DEPLOYMENT_MODE=oss confirmed
[VERIFY: confirm this was the actual value in .env during the test,
not assumed from the code default]), the API made real successful
outbound calls to Dograh's own servers:
  - POST https://services.dograh.com/api/v1/service-keys/     -> 200 OK
  - PUT  https://services.dograh.com/api/v1/cloudonix/domains/self -> 200 OK

Triggered from organization_bootstrap.py, which auto-provisions
"Dograh-managed model services" and "Dograh-managed SIP connectivity"
for every new organization, via mps_service_key_client.py
(create_service_key(), ensure_cloudonix_domain()).

This confirms the managed-platform code found in code review is NOT
dead/theoretical — it actively runs and reaches Dograh's infrastructure
on every signup, in default OSS mode. Must be disabled/removed before
any further testing that creates real accounts. Needs senior review
before deciding how (per Section 0 review gates — this borders on auth
and telephony provisioning).

FINDING B — Frontend: live Chatwoot widget loads Dograh assets on every page
Browser Network tab (filtered by ".com") shows ~20+ requests to
chat.dograh.com/widget on every page load, including Branding-*.js and
useBranding-*.js files.

Root cause traced: ui/src/app/layout.tsx renders <ChatwootWidget />
site-wide (line 90). ui/src/components/ChatwootWidget.tsx loads a live
chat script from Dograh's own Chatwoot instance at chat.dograh.com on
every page load. This is the source of the Branding.js/useBranding.js
requests seen in the Network tab.

Fix: [environment-variable controlled / needs code edit — fill in
after Step 2 investigation below]

FINDING C — Blocker for Finding B: UI runs a prebuilt Dograh image, not our source
Chatwoot URL/token not found in docker-compose.yaml or ui/.env.example.
Confirmed: the ui service runs dograhai/dograh-ui:latest, a PREBUILT
image pulled from Dograh's own container registry — NOT built from our
/ui source directory.

This means NEXT_PUBLIC_CHATWOOT_* values (and possibly
NEXT_PUBLIC_POSTHOG_KEY, see below) are likely baked into that image at
build time by Dograh, before they published it. Setting these vars in
our own .env may NOT override an already-compiled Next.js bundle —
Next.js inlines NEXT_PUBLIC_* vars at build time, not at container
start.

IMPLICATION: fixing Findings B may require building our OWN ui image
from our own /ui source (docker build, not docker pull) rather than
consuming Dograh's prebuilt image at all. This is arguably part of
what W1/W2 are meant to lead to anyway ("the same Docker image runs
both our shared multi-client instance and a dedicated per-client
instance" — that image needs to be ours). Flagging as a possible
scope addition to Task 3, not just a config fix.

1a. ENABLE_TELEMETRY controlled via api/constants.py:158, gated in
    app.py:18. Set to false LOCALLY in .env for testing.
    NOT YET FIXED IN SOURCE: constants.py default is still "true"

    Fix required: change default to "false" in constants.py.
    [Restart + browser Network-tab re-check still pending after fix.]

1b. PostHog is NOT gated by ENABLE_TELEMETRY — separate mechanism.
    Found in:
      - ui/src/app/api/config/posthog/route.ts (reads POSTHOG_KEY)
      - ui/src/instrumentation-client.ts (reads NEXT_PUBLIC_POSTHOG_KEY,
        calls posthog.init() directly if present, independent of the
        backend ENABLE_TELEMETRY flag)
    Setting ENABLE_TELEMETRY=false does NOT stop PostHog from
    initializing. This variable did not surface in the earlier
    "telemetry" keyword grep because the file doesn't contain that
    literal word — found only by reading actual init call sites.
    Fix needed: either (a) unset NEXT_PUBLIC_POSTHOG_KEY, or (b) make
    instrumentation-client.ts also check ENABLE_TELEMETRY before
    calling posthog.init(). (b) preferred — doesn't rely on every
    deployment remembering to leave a var blank.
    NOTE: same NEXT_PUBLIC_* prebuilt-image caveat as Finding C may
    apply here too — needs checking once the image-source question is
    resolved.
